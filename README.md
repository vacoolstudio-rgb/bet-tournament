# Bet Tournament

Сервис турнира на ставках: начисляет очки по событиям `bet.settled` из RabbitMQ
(**1 очко за 1 USD выигрыша**, валюты конвертируются по курсам из конфига),
отменяет начисление по `bet.rollback` и отдаёт лидерборд — топ-100 и позицию
игрока из заголовка `X-Player-Id`.

NestJS 12 (ESM) · PostgreSQL 18 · RabbitMQ 4 · TypeORM · amqplib

- [DECISIONS.md](DECISIONS.md) — какие вопросы оставило ТЗ и что я решил
- [AGENTS.md](AGENTS.md) — команды и инварианты для агентов и для себя-через-месяц
- [docs/data-model.md](docs/data-model.md) — трассировка каждого поля от payload до ответа
- [PLAN.md](PLAN.md) — план реализации и история проектных решений

## Быстрый старт

Весь стек в контейнерах, включая сервис:

```bash
cp .env.example .env           # продюсер и replay запускаются с хоста и читают его
docker compose up -d --wait    # postgres + rabbitmq + миграции + сервис на :3000
npm ci                         # для продюсера; сам сервис в контейнере
```

`--wait` ждёт, пока сервис станет healthy, то есть пока он реально достанет и
базу, и брокер. Миграции — отдельный одноразовый сервис `migrate`: приложение
стартует только после его успешного выхода, а упавшая миграция останавливает
деплой, а не оставляет сервис работать против схемы, которой он не ждёт.

`.env` нужен не контейнерам, а инструментам: сервис в compose получает все
переменные из `docker-compose.yml`. Compose подставляет из `.env` только
`LOG_LEVEL` и три `TOURNAMENT_*`, и значения в примере совпадают с дефолтами
compose — то есть копирование файла ничего не меняет для сервиса, кроме уровня
логов.

Для разработки — инфраструктура в контейнерах, сервис с хоста:

```bash
cp .env.example .env
docker compose up -d postgres rabbitmq   # management UI на :15672
npm ci
npm run db:migrate
npm run build && npm start               # :3000, или npm run start:dev
```

Прогнать события и посмотреть результат:

```bash
npm run produce -- --list                       # что умеет продюсер
npm run produce -- --scenario=happy             # 3 ставки в EUR, GBP, USD
curl -s localhost:3000/leaderboard | jq
```

Ответ на `happy` — один игрок с 48 очками: `10.40 EUR × 1.08 = 11.232`,
`10 GBP × 1.27 = 12.7`, `25 USD = 25`, итого `48.932`, в поле `points`
усечённые 48, в `pointsExact` — точное значение, по которому и шло
ранжирование.

```bash
npm run produce -- --scenario=rollback          # начислили и откатили
npm run produce -- --scenario=duplicate         # дубль не удваивает очки
npm run produce -- --scenario=unknown-currency  # уходит в парковку, а не в ноль
npm run produce -- --scenario=board --count=150   # 150 игроков: видно отсечку топ-100
npm run produce -- --scenario=chaos --count=200    # все формы событий сразу
npm run produce -- --scenario=load --count=5000
```

Если что-то ушло в парковку — например, ставка в валюте, которой не было в
`FX_RATES`, — его можно вернуть после правки конфига:

```bash
npm run replay -- --dry-run   # что лежит в парковке и почему, ничего не меняя
npm run replay                # вернуть всё обратно в exchange bets
```

Возврат ставит сообщение в тот же routing key, с которым оно пришло (он сохранён
в заголовке при парковке), и снимает с него `x-death` и park-заголовки: иначе
счётчик попыток продолжил бы прошлую жизнь сообщения и запарковал бы его
раньше времени. Сообщение без узнаваемого routing key остаётся в парковке —
угадывать хуже, чем оставить человеку.

На живом стеке: 5000 событий одному игроку (то есть максимальная конкуренция за
одну строку агрегата) обрабатываются примерно за 12 с, очки выходят ровно
`5000.000000` — ни один инкремент не потерян, — а лидерборд отвечает за 5 мс.

### Проверено под нагрузкой и в аварии

Три реплики консьюмера на одной очереди, `docker compose up -d --scale app=3`.
Главный инвариант во всех опытах — **агрегат равен журналу**:
`player_scores.points = SUM(bets.points_awarded WHERE status='settled')`.
Лидерборд — производное представление, и оно обязано сходиться с тем, из чего
выведено, как бы гонки ни разрешились.

| Опыт | Результат |
|---|---|
| Хаос: 400 сообщений, все формы событий сразу, чередуясь, один игрок | 400 из 400 подтверждено, агрегат = журналу, парковка пуста. Исходы сошлись по конструкции: 160 начислено + 80 дублей + 80 откатов + 40 надгробий + 40 «уже откатано» |
| `SIGKILL` реплике на 3000 событиях | 3000 в журнале, ровно `3000.000000` очков: 52 повторные доставки съела идемпотентность |
| `SIGTERM` реплике на 800 сообщениях + 300 параллельных запросов лидерборда | все 300 ответов 200, медиана 11 мс, p95 36 мс; агрегат = журналу; контейнер вернулся по `restart: unless-stopped` |
| RabbitMQ остановлен на 6 с под нагрузкой 1000 событий | все 1000 дошли сами, агрегат = журналу, рестартов приложения 0 |
| Postgres остановлен под нагрузкой | `/health` → 503, сообщения ждут в retry-очереди, парковка пуста; БД вернулась → всё начислилось само |
| 500 параллельных чтений под записью | 500 из 500 ответов 200; ни одного ответа, где ранги не 1..n, очки не монотонны или `me` противоречит своей же строке в `top` |
| Логи трёх реплик за весь прогон | 0 deadlock, 0 необработанных rejection, 0 падений обработчика, 0 ошибок парковки, 0 строк ERROR |
| Авария БД **длиннее** бюджета (70 с против 40 с) | 30 с сообщения крутятся в retry-очереди, на 40-й паркуются с `attempts_exhausted` и `попыток: 5`; `npm run replay` возвращает их и они начисляются |
| Возврат 200 запаркованных | обработаны за 3 с, очки ровно `600 = 200 × 2.0 × 1.5`, парковка пуста |
| Повторный возврат тех же ставок | очки не изменились — идемпотентность накрывает и путь возврата |
| 21 враждебная нагрузка (вложенность, 1 МБ, инъекции, омоглифы, загрязнение прототипа) | ни одного падения; всё непригодное запарковано с причиной, агрегат = журналу |
| Миграции: откат и повторное применение | схема побайтово идентична (38 объектов), повторный прогон идемпотентен |
| Две гонки миграторов | с advisory-блокировкой оба процесса выходят с нулём, запись о миграции одна |
| Пересоздание контейнеров Postgres и RabbitMQ | данные и запаркованные сообщения выживают |
| Четыре волны по 3000 событий подряд | 12 000 обработано, сверка сошлась, память реплик 93 → 121 МиБ и стабилизировалась (+1–2 МиБ на волну, не рост на объём) |
| `/health` под нагрузкой, 120 опросов | все 200, p95 11 мс — готовность не флапает, пока идёт запись |
| Старт с битым конфигом | по строке на каждую переменную и код возврата 1, до того как стартует фреймворк |

Эндпоинты: `/leaderboard`, `/health`, `/metrics`, Swagger на `/api/docs`.

## Наблюдаемость

Три вещи, и каждая отвечает на свой вопрос.

**Метрики** — `/metrics`, формат Prometheus, собственный `Registry` (не
глобальный: две копии сервиса в одном процессе тестов иначе падают на
дублирующей регистрации).

| Метрика | Что отвечает |
|---|---|
| `bet_events_acknowledged_total{reason}` | сколько событий обработано и чем кончилось: `scored`, `duplicate`, `out_of_window`, `rolled_back`, `nothing_to_roll_back` |
| `bet_events_retried_total`, `bet_events_parked_total{reason}` | «мы ждём базу» против «мы сдались» — это разные инциденты |
| `bet_event_processing_seconds` | гистограмма времени обработки события |
| `http_server_requests_total{method,route,status}` | трафик API по **шаблону** маршрута |
| `http_server_request_duration_seconds` | латентность API |
| `nodejs_eventloop_lag_p99_seconds`, `nodejs_heap_size_used_bytes`, `process_*` | насыщение — то, о чём сервис не может доложить сам: консьюмер, который перестал успевать, в своих счётчиках выглядит здоровым |

Маршрут в метку идёт шаблоном (`/leaderboard`), никогда URL: путь, которого нет
в роутере, управляется тем, кто его запросил, и метка из него — это способ
нарисовать сколько угодно временных рядов, пока скрейп не ляжет. Непойманный
путь получает единственное значение `unmatched`.

**Трассы** — OpenTelemetry, OTLP/HTTP. Одна трасса на ставку, через очередь и
через процессы: `publish bets` → `tournament.bets process` → `START`, `INSERT`,
`COMMIT`. Сшивается заголовком `traceparent`, который инструментация amqplib
пишет при публикации и читает при доставке. `docker compose up` поднимает Jaeger,
UI на [localhost:16686](http://localhost:16686).

```
publish bets                     bet-tournament-producer  3.8 мс
  tournament.bets process        bet-tournament          25.1 мс
    pg-pool.connect                                       0.2 мс
    pg.query:START tournament                             0.5 мс
    pg.query:INSERT tournament                            7.8 мс   ← журнал ставки
    pg.query:INSERT tournament                            6.5 мс   ← агрегат очков
    pg.query:COMMIT tournament                            2.5 мс
```

Без коллектора (`OTEL_EXPORTER_OTLP_ENDPOINT` не задан) спаны всё равно
создаются и контекст всё равно распространяется — то есть `trace_id` в логах
работает и там, где смотреть трассы негде. `OTEL_ENABLED=false` выключает
совсем.

**Логи** — pino, одна JSON-строка на запись, с `trace_id` и `span_id` в каждой:

```json
{"level":30,"context":"ScoringService","trace_id":"4201a103200a821166f48eeef82c9421",
 "span_id":"81ce361a519fb97f","msg":"Bet c486cbe4… is outside tournament \"nov-2026\"…"}
```

Это и есть смысл затеи: сервис — несколько реплик на одной очереди, и «что
случилось с этой ставкой» — вопрос про строки, написанные разными процессами в
разное время. С общим `trace_id` ответ на него — один поиск, а не вечер
грепанья. `LOG_PRETTY=true` включает человекочитаемый вывод для локальной
работы; `x-player-id` в логах запросов замаскирован.

## Образ

Многостадийный Dockerfile: установка зависимостей, сборка `tsc`, рантайм с
`npm ci --omit=dev`. Собирается `tsc`, а не бандлером, по той же причине, по
которой приложение нельзя запускать через `tsx`: Nest внедряет по метаданным
декораторов, а esbuild их не эмитит.

Рантайм-слой запускается от непривилегированного пользователя `node`, несёт
`HEALTHCHECK` на `/health` и умеет две команды: запустить сервис
(`dist/src/main.js`) и применить миграции (`dist/tools/db.js migrate`).

Из прод-установки удалены `typescript`, `ts-node` и `@swc/core` — около 60 МБ
инструментов компиляции, которые подтягивают `typeorm` и `@nestjs/swagger`, но
в рантайме не загружаются: сущности и миграции передаются скомпилированными
классами, а не ищутся по `.ts`, и CLI-плагин Swagger не используется. Это
утверждение про внутренности зависимостей, поэтому оно проверяется, а не
принимается на веру — smoke-шаг в CI поднимает именно этот образ, применяет
миграции, отдаёт `/api/docs` и обрабатывает событие.

## Контракт событий

Схема из ТЗ, без добавленных обязательных полей:

```json
{
  "betId":     "4f2e...",       // UUID
  "playerId":  "9a1c...",       // UUID
  "currency":  "EUR",           // 3..10 заглавных букв или цифр
  "stake":     "10.0000",       // строка или число, ≤ 4 знаков
  "winAmount": "10.4000",       // то же; база для очков
  "settledAt": "2026-11-15T10:00:00.000Z"   // ISO-8601, зона обязательна
}
```

Routing keys: `bet.settled` и `bet.rollback`, topic-exchange `bets`.

**У `bet.rollback` обязателен только `betId` и `playerId`.** Остальные поля
принимаются, но в решении не участвуют — и это требование корректности, а не
упрощение: проверка валюты отправила бы легитимный откат в парковку, а проверка
окна турнира — проигнорировала бы его. В обоих случаях очки остались бы
начисленными навсегда. Сколько вычитать, известно из журнала ставок.

## Топология RabbitMQ

```
         bet.settled / bet.rollback
                     │
           ┌─────────▼──────────┐
           │ exchange: bets     │ topic, durable
           └─────────┬──────────┘
           ┌─────────▼────────────────────────────┐
           │ queue: tournament.bets               │ quorum
           │   prefetch 20                        │
           │   x-dead-letter-exchange: bets.retry │
           │   x-delivery-limit: 20               │ предел переотправок
           │                                      │ одной доставки
           └───┬──────────────────────────────┬───┘
   ретраябл-    │                             │ отравленное сообщение:
   ошибка:      │                             │ публикуем явно + ack
   reject       ▼                             ▼
      ┌─────────────────────┐    ┌─────────────────────────┐
      │ exchange bets.retry │    │ queue tournament.parked │
      └─────────┬───────────┘    └─────────────────────────┘
      ┌─────────▼────────────────┐
      │ queue tournament.retry   │ classic, x-message-ttl
      │   DLX → bets             │ возвращает с тем же routing key
      └──────────────────────────┘
```

Два исхода разведены намеренно. **Ретраябл-ошибка** (БД недоступна, deadlock) —
reject без requeue: сообщение уходит в retry-очередь, лежит там TTL и
возвращается. Счётчик попыток читается из `x-death`. **Отравленное сообщение**
(битая схема, неизвестная валюта) — консьюмер сам публикует его в
`tournament.parked` с причиной в заголовках и подтверждает. Requeue на месте
переотправил бы мгновенно и сжёг все попытки за миллисекунды.

## Конфигурация

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | `postgres://` или `postgresql://` |
| `DATABASE_POOL_MAX` | соединений в пуле. По умолчанию `RABBITMQ_PREFETCH + 5`: доставка обрабатывается в транзакции, поэтому меньший пул заставит обработчики ждать соединение, и пропускная способность упадёт без следа в логах |
| `RABBITMQ_URL` | `amqp://` или `amqps://` |
| `RABBITMQ_PREFETCH` | сколько неподтверждённых сообщений держит консьюмер (20) |
| `RABBITMQ_MAX_ATTEMPTS` | попыток до парковки (5) |
| `RABBITMQ_RETRY_TTL_MS` | задержка перед возвратом из retry-очереди (10000) |
| `FX_RATES` | JSON: сколько USD в единице валюты. `USD` указывать нельзя — его курс 1 по определению |
| `TOURNAMENT_CODE` | код активного турнира |
| `TOURNAMENT_STARTS_AT` / `TOURNAMENT_ENDS_AT` | окно турнира: начало включительно, конец исключительно |

Конфиг валидируется zod'ом на старте: процесс не поднимется с курсом `"abc"`,
отрицательным курсом, `USD` в таблице курсов или окном, которое кончается
раньше, чем начинается. Ошибка печатается по строке на переменную, до запуска
фреймворка:

```
Configuration is invalid:
  PORT: Invalid input: expected number, received NaN
  FX_RATES: USD must not be listed in FX_RATES: its rate is hardcoded to 1
```

## Допущения

Там, где ТЗ допускает несколько чтений, выбор зафиксирован в
[DECISIONS.md](DECISIONS.md). Коротко о том, что меняет поведение:

- **`X-Player-Id` — это идентификация, не аутентификация.** Заголовок принят на
  доверии, потому что так написано в ТЗ. В проде id приходит из проверенного
  токена; подставить чужой заголовок здесь может кто угодно.
- **Очки = `winAmount` в USD**, не чистая прибыль. Хранятся точно
  (`NUMERIC(20,6)`), в API отдаются и усечёнными (`points`), и точными
  (`pointsExact`) — ранжирование идёт по точным, поэтому два игрока могут
  показывать одинаковые 48 и стоять на разных местах.
- **Окно турнира** (`TOURNAMENT_STARTS_AT`/`ENDS_AT`) — зачем в схеме события
  вообще нужен `settledAt`. Ставки вне окна подтверждаются и не начисляют
  очков, **но говорят об этом в лог**, с обеими датами рядом:

  ```
  Bet cc5d2d95… settled at 2027-03-15T12:00:00.000Z is outside tournament
  "nov-2026" (2026-11-01T00:00:00.000Z .. 2026-12-01T00:00:00.000Z), so it
  scores nothing
  ```

  Иначе событие, посланное руками с датой не из окна, выглядит как «ничего не
  произошло»: в журнале пусто, в логах пусто, и единственный след — счётчик
  `bet_events_acknowledged_total{reason="out_of_window"}` в `/metrics`. Сдвиг
  окна в конфиге **не** пересчитывает уже начисленное.
- **Суммы — мажорные единицы** (`"10.4000"`, не `104000`), до 4 знаков,
  до 10¹². Арифметика на `decimal.js` с точностью 40 значащих цифр; `number`
  рядом с деньгами не появляется нигде.
- **Лидерборд — доска тех, кто набрал.** Игрок с нулём очков не имеет позиции:
  его нет в топе и `me.rank` для него `null`, независимо от того, не делал он
  ставок или все они откатаны.

## Тесты

```bash
npm run test              # 370 юнит-тестов, без инфраструктуры
npm run test:integration  # 149 тестов на настоящих Postgres и RabbitMQ
npm run verify            # typecheck + lint + формат + юнит
```

Интеграционные поднимают контейнеры через Testcontainers — нужен запущенный
Docker, компоуз для них не используется. Один Postgres и один RabbitMQ на весь
прогон, около трёх минут.

Отдельный набор обрывает соединение сервиса со стороны брокера (management API,
`DELETE /api/connections/{name}`) и проверяет, что сервис сам заметил, сам
переподключился, заново объявил удалённую очередь и продолжил начислять, а в
промежутке честно отвечал 503 на `/health`. Ничего не рестартуется руками —
иначе проверялся бы рестарт, а не восстановление.

Разделение осознанное: юнит-тесты проверяют **оркестрацию** на подставленных
ответах портов, а не переписывают семантику SQL в фейках. `ON CONFLICT DO
NOTHING`, условный `UPDATE … WHERE status = 'settled'` и атомарный инкремент —
это как раз то, что достойно проверки, и рукописный фейк доказывал бы лишь, что
он согласен сам с собой. Поэтому «что сервис делает с данным ответом» — в
юнитах, «Postgres правда отвечает так» — в интеграционных.

## CI

[`.github/workflows/ci.yml`](.github/workflows/ci.yml), три джобы:

- **types, lint, unit** — `typecheck`, `lint`, `format:check` и юнит-тесты с покрытием. Пороги — часть контракта: падение покрытия домена роняет сборку, а не замечается потом;
- **integration** — те же 119 тестов на настоящих Postgres и RabbitMQ через Testcontainers, против докер-демона раннера. `docker-compose.yml` для них не используется, поэтому прогон и локальный стек не могут помешать друг другу;
- **image** — собирает образ, поднимает весь стек с `--wait` и проверяет, что миграции прошли отдельным шагом, а эндпоинты отвечают. Успешная сборка доказывает, что Dockerfile компилируется, а `--wait` — что сервис дотянулся до базы и брокера.

## Что сознательно не делалось

Аутентификация и ACL; несколько одновременных турниров; исторические курсы
(берётся текущий, но применённый курс сохраняется в строке ставки); Redis-кеш
лидерборда — на 50 000 игроков худший замеренный случай около 6 мс, запас
большой; outbox — сервис ничего не публикует наружу, кроме перекладывания
отравленных сообщений.

# AGENTS.md

Инструкции для агентов, работающих в этом репозитории, и для себя-через-месяц.
Формат — по [agents.md](https://agents.md/): обычный markdown, ближайший к
файлу AGENTS.md выигрывает, явная просьба человека важнее этого файла.
Репозиторий одномодульный, поэтому файл один, вложенных нет.

Человеческое описание сервиса — в [README.md](README.md), обоснования решений —
в [DECISIONS.md](DECISIONS.md). Здесь только то, что нужно, чтобы менять код и
не сломать деньги.

## Setup commands

```bash
docker compose up -d --wait            # весь стек: инфраструктура + миграции + сервис

cp .env.example .env                   # или для разработки с хоста:
docker compose up -d postgres rabbitmq
npm ci
npm run db:migrate                     # db:revert и db:show тоже есть
npm run build && npm start
npm run produce -- --list              # сценарии для прогона событий вручную
npm run replay -- --dry-run            # что лежит в парковке; без --dry-run вернёт обратно
```

`npm run start:dev` собирает в watch-режиме и перезапускает `dist`. **Через
`tsx` приложение запускать нельзя:** esbuild не поддерживает
`emitDecoratorMetadata`, поэтому у всех конструкторов исчезают типы и Nest не
может ничего внедрить. Для `tools/*` tsx годится — там нет DI.

## Code style

- TypeScript strict, ESM (NestJS 12 поставляется только как ESM). Относительные импорты **с расширением `.js`**.
- Никаких `any` в домене; `npm run lint` держит `no-unsafe-*` включёнными.
- Деньги и очки — только `decimal.js` и десятичные строки. `number` рядом с деньгами — ошибка; единственное исключение — `points` в HTTP-ответе, где это усечённое целое.
- Контракты (интерфейсы, порты, токены) живут в `*/contracts/` и `*.contract.ts`; классы — адаптеры под них. Сервисы инжектятся по токенам, чтобы тест подставлял объект, а не поднимал TypeORM. **Ни одного исключения:** если нужному вызову нет порта — порт добавляется, а не инжектится класс. Короче всегда второе, поэтому правило держит тест (`test/unit/messaging/broker-ports.spec.ts`).
- В домен входит разобранное (`Decimal`, `Date`), из домена выходит текст (точные десятичные строки) — он идёт в логи, метрики и HTTP.

## Testing instructions

```bash
npm run test              # юнит, без инфраструктуры
npm run test:integration  # нужен запущенный Docker (Testcontainers)
npm run verify            # typecheck + lint + format:check + юнит
```

- Юнит-тесты подставляют **ответы портов**, а не переписывают SQL в фейках. Семантику `ON CONFLICT`, условного `UPDATE` и атомарного инкремента проверяют интеграционные — на настоящем Postgres.
- `npm run test:cov` считает только юнит-набор, поэтому адаптеры из него исключены (см. комментарий в `vitest.config.mts`). Не «починяйте» ноль покрытия юнит-тестами SQL против мока.
- Интеграционные используют один Postgres и один RabbitMQ на весь прогон (`globalSetup`). Порядок подготовки в `consumer.spec` важен: остановить приложение → очистить очереди → очистить таблицы → поднять заново. Иначе предыдущий консьюмер допишет строки в только что очищенную базу.
- Новый тип события или новый исход — новый интеграционный тест. Исходы (`SettleOutcome`, `RollbackOutcome`, `AckReason`) перечислимы специально, чтобы забыть ветку было нельзя.

## PR instructions

- Коммиты в императиве, с объяснением *почему*, а не *что*: диффу видно, что изменилось.
- `npm run verify` перед пушем; интеграционные — перед любым изменением в `src/database`, `src/messaging` или миграциях.
- Миграции только добавлением. Правка существующей миграции допустима лишь пока она не ушла дальше этого репозитория.

## Инварианты, которые нельзя ломать

Каждый из них — чей-то проигранный выигрыш, если сломать.

1. **Деньги не `number`.** Точность `decimal.js` поднята до 40 значащих цифр: при дефолтных 20 хвост произведения суммы на 8-значный курс молча округляется, а откат обязан вычесть ровно то число, которое начислил settle.
2. **Откат вычитает `points_awarded` из строки ставки**, а не пересчитывает по текущему курсу. Курс в конфиге мог измениться между событиями. Пересчёт невыразим (инвариант 3), и это закреплено `@ts-expect-error`-стражем в `test/unit/scoring/rollback-shape.spec.ts`: расширите `RollbackBetCommand` или `VoidedBet` — упадёт `tsc`, а не тест через полгода.
3. **`bet.rollback` не резолвит курс и не проверяет окно турнира.** В `RollbackBetCommand` нет ни валюты, ни времени — так эти две ошибки просто невыразимы. Не добавляйте туда поля.
4. **Журнал решает, чьи это очки.** Если `playerId` в событии отката не совпадает с журналом, списывать нужно у того, кому начислил settle.
5. **`last_scored_at` двигается только при `points_awarded > 0`** и пересчитывается при откате. Иначе проигранная ставка меняет позицию игрока, не меняя его очков.
6. **`rank = null` ⟺ `points = 0`**, и такой игрок не попадает в топ. Игрок без ставок и игрок, у которого всё откатили, обязаны получить один и тот же ответ.
7. **ack только после коммита.** Падение между коммитом и ack даёт переотправку, которую съедает идемпотентность; обратный порядок теряет событие. Держится формой `settle` — `await handler(...)`, затем ответ, — и наблюдается снаружи в `test/integration/delivery-settlement.spec.ts` через счётчик неподтверждённых доставок брокера.
8. **Сообщение, которое не удалось запарковать, не подтверждается.** Иначе тело падает на пол.
9. **`x-death` читается как сумма `count` по записям главной очереди**, не как число записей и не как первая подходящая. Сообщение покидает очередь по двум причинам (`rejected` и `delivery_limit`), у каждой своя запись.
10. **Схема — только миграциями**, `synchronize` выключен и остаётся выключенным; `migrationsRun` тоже — миграции идут из CLI и из одноразового compose-сервиса, где сбой виден и упорядочен, а не из реплики, стартующей наперегонки с двумя другими. Проверяет `test/unit/database/data-source.spec.ts`.
11. **Рантайм-образ удаляет `typescript`, `ts-node` и `@swc/core`** (их тянут `typeorm` и `@nestjs/swagger`, в рантайме они не нужны). Если появится зависимость или путь, которым они нужны **во время работы**, уберите `rm -rf` из Dockerfile — иначе образ упадёт на `MODULE_NOT_FOUND` там, где локально всё работает. Smoke-шаг в CI поднимает именно этот образ и поймает это.
12. **Подтверждение доставки обёрнуто в try/catch, потому что на мёртвом канале оно бросает.** При закрытии канала amqplib подменяет `sendImmediately` на функцию, которая кидает `IllegalOperationError('Channel closed')` (`node_modules/amqplib/lib/channel.js`, `invalidateSend`). Обработка запускается отцеплённой (`void this.settle(...)`), поэтому такой бросок — необработанное отклонение, а Node по умолчанию на этом завершает процесс: сервис логически переживал обрыв и честно отвечал 503, но не доживал до переподключения. Делать с ошибкой нечего — неподтверждённая доставка уже вернулась в очередь, — поэтому её достаточно залогировать. Держит `test/integration/delivery-settlement.spec.ts`: обработчик удерживается открытым, соединение рвётся, обработчик отпускается; без try/catch тест падает с `IllegalOperationError: Channel closed`. Слушатель `channel.on('error')` рядом — **только для логов**: `amqp-connection-manager` обрабатывает событие канала сам, и его снятие на этом тесте ничего не меняет (проверено).

13. **Конфликт надгробия — не «уже откатано».** Если `insertTombstone` вернул false, строка появилась между двумя операторами, и единственная причина — начисление закоммитилось, пока откат решал, что откатывать нечего. Надо посмотреть ещё раз (`markRolledBack` повторно) и списать. Прочитать конфликт как дубль значит оставить очки навсегда — проверено: без этой повторной попытки из 15 пар «начисление + откат залпом» откатывается 4.
14. **Из `validateEvent` не должно вылетать ничего, кроме `PoisonMessageError`.** Трансформер и валидатор умеют бросать (глубокая вложенность валит стек), а любая другая ошибка оттуда будет прочитана как инфраструктурная и уедет в ретраи на весь бюджет — пять доставок на нагрузку, которая не прочитается никогда.
15. **`UPDATE … RETURNING` через TypeORM заворачивается в CTE и селектится.** Напрямую драйвер возвращает `[строки, количество]`, и тогда `rows.length === 0` не наступает никогда — `markRolledBack` перестаёт сообщать «нечего откатывать», а двойной откат списывает дважды.
16. **`src/observability/tracing.ts` — первый импорт процесса.** Инструментации патчат `amqplib`, `pg` и `http` по мере их загрузки, поэтому модуль, загруженный до старта SDK, не трассируется никогда — и сломать это можно, просто отсортировав импорты в `main.ts` по алфавиту. То же в `tools/*`: без этого опубликованное руками событие не попадает ни в одну трассу. Короткоживущий процесс обязан дождаться `shutdownTracing()` — иначе спаны остаются в буфере, который умирает вместе с ним.
17. **В метку метрики идёт шаблон маршрута, никогда URL.** Путь, которого нет в роутере, выбирает тот, кто его запросил; метка из него — это способ нарисовать сколько угодно временных рядов, пока скрейп не ляжет. Непойманный путь получает единственное значение `unmatched`. По той же причине в метки не попадают `betId` и `playerId`.
18. **У `MetricsService` свой `Registry`.** Не глобальный: в интеграционных тестах в одном процессе живут две копии сервиса, и на глобальном реестре второй конструктор падает на дублирующей регистрации — падает то, что к тесту отношения не имеет.
19. **Брокер отвечает на три токена, по одному на вызывающего:** `BROKER` — публикация, `BROKER_CONSUME` — приём, `BROKER_HEALTH` — готовность. Один провайдер за `useExisting`, иначе получится три соединения и health-check, докладывающий о том, из которого никто не читает. Разделены они потому, что половины нужны разным местам: паркующий публикатор только публикует, консьюмер только читает, — а один интерфейс заставил бы каждого зависеть от чужой половины и тащить её в фейк.
20. **`withTransaction` запрашивает `READ COMMITTED` явно, а не берёт серверный дефолт.** От этого уровня зависит инвариант 13: откат, проигравший гонку своему начислению, списывает очки только потому, что оператор после конфликта надгробия видит свежий снимок. Замерено теми же операторами на обоих уровнях: при repeatable read вставка надгробия поднимает `could not serialize access due to concurrent update`, транзакция обрывается, ставка остаётся `settled`. Сервис всё равно сходится (ошибка retryable, работа идемпотентна), но платит доставкой, а бюджет попыток конечен. `default_transaction_isolation` настраивается на базу и на роль, поэтому без явного аргумента инвариант домена зависел бы от настроек сервера. Держит `test/integration/transaction-isolation.spec.ts` — соединение в нём намеренно настроено на repeatable read.
21. **Новое поле в ответе API требует `@ApiProperty`.** DTO связаны с контрактами через `implements`, поэтому поле нельзя забыть в классе — но `implements` ничего не знает о декораторе, и без него API отдаёт поле, а опубликованная схема его не описывает. Именно так `limit` оказался валидируемым и незадокументированным. Проверяет реальный ответ против реального документа в `leaderboard.api.spec.ts`.
22. **`x-delivery-limit` не ограничивает retry-цикл.** Он ограничивает повторные доставки *внутри одного пребывания в очереди* — обработчик, умерший не подтвердив, или доставку, повторённую после обрыва соединения. Отклонённое сообщение уходит из очереди и возвращается уже новым, со счётчиком доставок, начатым заново: замерено — при лимите 3 тридцать доставок за двенадцать секунд, причина `delivery_limit` в `x-death` не появилась ни разу. Цикл заканчивает `RABBITMQ_MAX_ATTEMPTS`, считаемый из `x-death`. Не опирайтесь на лимит как на страховку и не поднимайте `maxAttempts` в расчёте, что брокер подстрахует.
23. **Масштабы денег живут в трёх местах, и два из них теперь производные.** `MONEY_SCALE`, `RATE_SCALE`, `POINTS_SCALE` и `COLUMN_PRECISION` в `common/money.ts` — источник; декораторы сущностей их импортируют; SQL миграции не может, поэтому его сверяет `test/integration/column-scales.spec.ts`. Расхождение молчаливо: Postgres округляет значение до масштаба колонки без единого слова (`1.12345678::numeric(20,6)` → `1.123457`, вверх), а очки в этом сервисе везде усекаются. Тест на дрейф схемы это не поймает — при смене одной константы сущности и база остаются в полном согласии.
24. **`numeric` обязан приходить из драйвера строкой.** На этом держится решение хранить точный decimal, а не целые минорные единицы: `numeric` в Postgres точен, и значение не попадает в `double`, пока `pg` отдаёт его текстом. `pg.types.setTypeParser(1700, parseFloat)` — частый способ сделать `numeric` «удобнее» — молча превратит деньги в float, и остальные тесты это пропустят, потому что в тестах числа мелкие. Проверяет `test/integration/column-scales.spec.ts`; с таким парсером он падает тремя проверками, включая `MAX_POINTS` → `100000000000000`.
